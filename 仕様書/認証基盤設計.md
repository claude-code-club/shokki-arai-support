# 認証基盤設計（第17回、調査・設計フェーズ）

第16回（マルチテナント設計、staging正式完了）を土台に、ログイン認証を導入する。**この文書は調査・設計と、Auth0の外部設定を必要としない範囲の実装のみを対象とする。Auth0アカウント作成・秘密値の入力・callback URL登録はoperator本人が行うため、このタスクの範囲外。productionへは反映しない。**

## 前提（確定事項）

- 第一候補：Streamlit標準のOIDC認証（`st.login`/`st.user`/`st.logout`）＋認証プロバイダーはAuth0
- Auth0がアカウント作成・メール確認・ログイン・ログアウト・パスワード再設定を担う。**アプリDBはパスワードを一切保存しない**
- Auth0のOIDC subject（`sub`）をユーザー識別子として`users`テーブルへ保存する
- `tenant_memberships`でユーザーと世帯（tenant）とroleを紐付ける。roleは`admin`／`member`の2種類
- `tenant_id`はブラウザ入力・URLパラメータからは一切決めない。ログインユーザーの`sub`からサーバー側で解決する
- productionには反映しない

## ① 調査結果

| # | 項目 | 結果 |
|---|---|---|
| 1 | 現在のStreamlitバージョン | ローカルpip確認で`1.61.1`（`requirements.txt`はpin無し。ビルド時にlatestが入る前提）。`st.login`系はStreamlit 1.42.0で導入され現行版まで維持されているため問題なし |
| 2 | `st.login`/`st.user`/`st.logout`の利用可否 | 利用可能。ただし追加で**`Authlib>=1.3.2`が必須**（`streamlit[auth]`または`Authlib`を直接インストール）。未インストールだと`StreamlitAuthError`で明示的にエラーになる |
| 3 | Auth0の公式OIDC設定方法 | Auth0で「Regular Web Application」種別のアプリケーションを作成し、Allowed Callback URLs・Allowed Logout URLsを設定。`client_id`・`client_secret`・OIDC discovery URL（`server_metadata_url`）を`secrets.toml`の`[auth.auth0]`へ設定する |
| 4 | メール確認・パスワード再設定・ログアウトがUniversal Loginで可能か | 可能。Auth0の標準データベース接続は、サインアップ時のメール確認リンクと、ログイン画面の「Don't remember your password?」からのパスワード再設定を**追加実装なしの標準機能**として提供する |
| 5 | staging URLに必要なcallback/logout URL | Callback URL：`https://web-staging-beab.up.railway.app/oauth2callback`（Streamlitの仕様で`/oauth2callback`固定）。Logout URL：`https://web-staging-beab.up.railway.app`（`st.logout()`はアプリのホームページへ戻す仕様のため） |
| 6 | `secrets.toml`をRailway環境変数から安全に設定できる構成 | **Streamlit公式には環境変数からの直接読み込みは現時点で未対応**（`[auth]`設定は`secrets.toml`ファイルのみ。GitHub Issue #10543で機能要望として提起されているが未実装）。RailwayはファイルではなくREST変数のみサポートするため、**コンテナ起動時にRailway環境変数から`secrets.toml`を生成するスタートアップスクリプト**を導入する（Railway利用者コミュニティで一般的な回避策。⑭参照） |
| 7 | 現在の依存関係への影響 | `Authlib`の追加が必要。Authlib 1.6.6に既知の不具合報告があるため、`Authlib>=1.3.2,!=1.6.6`のように除外ピンを行う |

**結論**：重大な障害はないため、Auth0案を採用する。

## ② Auth0とアプリDBの責任分担

| 領域 | 担当 |
|---|---|
| アカウント作成・サインアップフォーム | Auth0（Universal Login） |
| メール確認 | Auth0（標準機能） |
| パスワードの保存・検証 | Auth0のみ。**アプリDBは一切保存しない** |
| パスワード再設定 | Auth0（標準機能） |
| ログイン・ログアウト（セッション） | Streamlit（`st.login`/`st.logout`）が仲介、実体はAuth0 |
| 「どのユーザーがどの世帯にどのroleで所属しているか」 | アプリDB（`tenant_memberships`）のみが真実の源 |
| `email`／`email_verified`のアプリDB側の値 | Auth0側の値をログインの都度同期する、あくまで表示・監査用のキャッシュ（真実の源はAuth0） |

## ③ `users`テーブル

```sql
CREATE TABLE users (
    id             UUID PRIMARY KEY,
    auth_subject   TEXT UNIQUE NOT NULL,  -- Auth0のsub（例: "auth0|65f..."）
    email          TEXT,
    email_verified BOOLEAN NOT NULL DEFAULT false,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

---

## ④ `tenant_memberships`テーブル

```sql
CREATE TABLE tenant_memberships (
    tenant_id  UUID NOT NULL REFERENCES tenants(id),
    user_id    UUID NOT NULL REFERENCES users(id),
    role       TEXT NOT NULL CHECK (role IN ('admin', 'member')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, user_id)
);
```

複合主キー`(tenant_id, user_id)`により`UNIQUE(tenant_id, user_id)`を自然に満たす。`tenants`は第16回で既に存在するテーブルを参照する。

## ⑤ 将来の複数世帯所属、現段階の制約

- テーブル設計上は「1ユーザーが複数の`tenant_memberships`を持つ」ことを制約せず許容する（将来、実家と自分の家など複数世帯に参加するケースに対応できる）
- **第17回時点のapp.pyは1ユーザー1世帯を前提とする**。ログインユーザーのmembershipが2件以上ある場合は、現状未対応として安全側に倒し、「複数世帯対応は準備中です」を表示して`st.stop()`する（⑦参照）

---

## ⑥ 初回ユーザーを初期世帯adminへ紐付ける方法（招待方針）

- **自動紐付けは一切行わない**。`scripts/bootstrap_admin_membership.py`（新規、一回限りの管理スクリプト）を用意し、operatorが対象ユーザーの`auth_subject`と`tenant_id`を明示的に指定して実行した場合のみ、adminとして紐付ける
- メールアドレスだけを条件に自動的に初期世帯へ参加させることはしない
- 未登録ユーザー（Auth0でサインアップしただけで`tenant_memberships`が未作成）は、ログインはできるが「どの世帯にも所属していません」の画面で停止する（⑧参照）。**一般ユーザーの自動サインアップだけでは、どの世帯にも所属しない状態になる**

---

## ⑦ ログイン→membership解決→tenant_id決定→DB操作の流れ

1. `app.py`起動時、`st.user.is_logged_in`を確認する。未ログインなら`st.login()`を呼ぶボタンを表示して停止する
2. ログイン済みなら`st.user["sub"]`（Auth0の`sub`）を取得し、`users`テーブルを`auth_subject`で検索する。無ければ新規作成し、`email`/`email_verified`をAuth0側の最新値で同期する
3. `tenant_memberships`から、そのユーザーの所属一覧を取得する
   - **0件**：`AccessDeniedError`（「どの世帯にも所属していません。管理者にお問い合わせください」を表示して`st.stop()`。⑧参照）
   - **2件以上**：`AccessDeniedError`（「複数世帯への所属には現在対応していません」を表示して`st.stop()`。⑤参照）
   - **1件**：その`tenant_id`と`role`を確定し、以降の`storage`呼び出しへ渡す
4. `role`に応じてUIの操作範囲を制御する（⑨参照）

この解決ロジック（`auth.resolve_tenant_context()`）は`conn`と`auth_subject`/`email`/`email_verified`を引数に取る**純粋なDB操作関数**として実装し、Streamlitの実行時コンテキストに依存させない。これにより、実際のAuth0接続が無くても`pytest`で完全に検証できる。

---

## ⑧ 認証済みでもmembershipがなければ利用拒否

上記⑦-3のとおり。ログイン自体は成功しても、`tenant_memberships`に対応する行が無ければ、記録データへは一切アクセスさせない。

## ⑨ admin／memberの操作範囲

- 記録の閲覧・追加・取り消しには、第17回時点ではadmin/memberで機能差を設けない（世帯内の家族全員が対等に記録する、という第16回の設計とも整合する）
- 将来のadmin専用操作（世帯メンバーの招待・削除等）は第17回では実装しない
- **第17回では、role基盤の動作確認のためだけに、最小限のadmin専用操作を1つ用意する：世帯名（`tenants.name`）の変更**。member権限では実行できず、サーバー側（DB操作の直前）でもrole検証を行う（表示を隠すだけにしない）

---

## ⑩ セッション・ログアウト・エラー時の扱い

- セッションは`st.login()`が発行するcookie（`cookie_secret`使用）で維持する。有効期限はStreamlit既定に従う
- ログアウトボタンから`st.logout()`を呼ぶ。Streamlit公式仕様により、Auth0側のセッションも含めて破棄され、アプリのホームページへ戻る
- エラー時（Auth0接続失敗、OIDC設定不備等）は、詳細を画面に出さず一般向けメッセージ＋`st.stop()`とする（第16回の`StorageConfigError`等と同じ方針）
- セッション情報・OIDCクレームは**ログへ丸ごと出力しない**（`st.user`の中身をそのまま`print`/`log`しない。使うのは`sub`/`email`/`email_verified`の3値のみ）

---

## ⑪ 第16回の`DEFAULT_TENANT_ID`から認証連動への切り替え手順

- 新しい環境変数**`AUTH_ENABLED`**（`true`／未設定、既定は未設定＝無効）を導入する
- `AUTH_ENABLED`が未設定の間は、**第16回の`DEFAULT_TENANT_ID`方式のまま動作**し、認証まわりのコードパス（`st.login`等）には一切入らない（現在のstaging動作に影響しない）
- `AUTH_ENABLED=true`の場合のみ、ログイン必須＋membership解決フローに入り、`DEFAULT_TENANT_ID`は参照しなくなる
- 切り替え手順：①`scripts/bootstrap_admin_membership.py`で最初の管理者を初期世帯へ紐付け →②Auth0側の設定（callback/logout URL、Client ID/Secret）をoperatorが完了 →③Railway環境変数（`AUTH0_*`・`COOKIE_SECRET`等）を設定 →④staging実機で一通り確認 →⑤`AUTH_ENABLED=true`をstaging/webへ設定

---

## ⑫ 切り戻し方法

- `AUTH_ENABLED`を未設定に戻せば、即座に第16回の`DEFAULT_TENANT_ID`方式へ戻る（コードは両方式を保持したまま、両立させる設計）
- `users`／`tenant_memberships`テーブルは切り戻し時も削除しない（再度`AUTH_ENABLED=true`にする際にそのまま使える）

## ⑭ 秘密値のRailwayへの設定（Streamlitのファイル前提への対応）

Streamlitの`[auth]`設定は`secrets.toml`ファイルのみを読む仕様（①-6参照）のため、Railwayの環境変数から以下の手順でファイルを生成する。

- `scripts/write_streamlit_secrets.py`（新規）：Railway環境変数（`AUTH0_CLIENT_ID`・`AUTH0_CLIENT_SECRET`・`AUTH0_DOMAIN`・`COOKIE_SECRET`・`APP_BASE_URL`）を読み、`.streamlit/secrets.toml`をコンテナのローカルディスクへ生成する。**`AUTH_ENABLED`が未設定の場合は何もせず終了する**（既存の非認証環境に影響しない）
- `Procfile`の起動コマンドを`python scripts/write_streamlit_secrets.py && streamlit run streamlit/app.py ...`のように変更し、Streamlit起動前に必ず実行する
- 生成された`.streamlit/secrets.toml`は**コンテナの一時ディスク上にのみ存在し、Gitには一切コミットしない**（`.gitignore`へ`.streamlit/secrets.toml`を追加）。デプロイのたびに環境変数から再生成されるため、コンテナが再作成されても問題ない
