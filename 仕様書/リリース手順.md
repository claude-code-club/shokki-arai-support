# リリース手順（push→本番URL）

Git×Railway上級マスター・速習編 第8回で整理した、食器洗いサポートの自分専用リリース手順。

---

## 全体の流れ

```
① 作業ブランチで変更
    ↓ git push
② stagingブランチへ反映（または直接PR作成）
    ↓ Railwayが自動検知
③ staging環境に自動デプロイ
    ↓ web-staging-beab.up.railway.app で実機確認
④ 問題なければ PR 作成（対象: main）
    ↓ ChatGPTレビュー → Approve
    ↓ ユーザー最終承認
⑤ mainへマージ
    ↓ Railwayが自動検知
⑥ production環境に自動デプロイ
    ↓ web-production-0b8c5f.up.railway.app で実機確認（PC・スマホ両方）
⑦ 完了
```

---

## 手順（実際のコマンド）

1. `git checkout staging && git pull origin staging`
2. コードを変更する
3. `git add <ファイル> && git commit -m "変更内容"`
4. `gh auth switch --user claude-code-club`（GitHub操作前に必ず切り替え）
5. `git push origin staging`
6. Railwayのstaging環境（`web-staging-beab.up.railway.app`）が自動デプロイされるのを待ち、実機で確認
7. 問題なければ `gh pr create --base main --head staging`
8. ChatGPTへPRのURLを渡してレビューを依頼
9. Approveをもらったらユーザーが最終承認
10. `gh pr merge <PR番号> --merge`（`--delete-branch` は付けない。staging環境用の持続ブランチのため削除してはいけない）
11. `gh auth switch --user iwasegiken`（作業後は必ず戻す）
12. productionのRailway自動デプロイを待ち、本番URL（`web-production-0b8c5f.up.railway.app`）をPC・スマホ両方で確認

---

## 安全のためのルール

- **`main`へ直接pushしない**。必ずブランチ→PR→レビュー→承認→マージの順を守る
- **`staging`ブランチは削除しない**。environment（Railway側のstaging環境）がこのブランチ名と紐付いているため、削除すると次回作業前に作り直しが必要になる（第7回で実際に発生した事故）
- ChatGPTレビューが「条件付きApprove」の場合、本番反映後の実機確認まで済ませてから完了とする
- 秘密情報（APIキー等）はコードに書かず、Railwayの環境変数（production／staging双方）に登録する
- production環境はユーザーが日常的に使うため、stagingで十分確認してからマージする

---

## 既知の制約（このアプリ固有）

- Railwayのコンテナ再起動（再デプロイ含む）のたびに記録データが消える（データ非永続化の既知課題。今後のDB回で対応予定）
- 依存パッケージはルート`requirements.txt`と`streamlit/requirements.txt`の2箇所に重複しているため、パッケージ追加時は両方を更新する
