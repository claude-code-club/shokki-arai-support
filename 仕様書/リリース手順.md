# リリース手順（push→本番URL）

Git×Railway上級マスター・速習編 第8回で整理した、食器洗いサポートの自分専用リリース手順。

---

## 全体の流れ

```
① feature/xxx ブランチ（mainから作成）で変更
    ↓ git push
② staging ブランチへ反映（feature/xxx を merge）
    ↓ Railwayが自動検知
③ staging環境に自動デプロイ
    ↓ web-staging-beab.up.railway.app で実機確認
④ 問題なければ staging → main へPR作成
    ↓ ChatGPTレビュー → Approve
    ↓ ユーザー最終承認
⑤ mainへマージ
    ↓ Railwayが自動検知
⑥ production環境に自動デプロイ
    ↓ web-production-0b8c5f.up.railway.app で実機確認（PC・スマホ両方）
⑦ 完了
```

**`staging`は直接開発する場所にしない。** 実際の作業は必ず`feature/xxx`で行い、検証したい状態がまとまったらstagingへ反映（merge）する。stagingは「持続する検証環境」であり、そのまま`main`へのPRの土台になる。

---

## 手順（実際のコマンド）

1. `git checkout main && git pull origin main`
2. `git checkout -b feature/xxx`（作業ブランチをmainから作成）
3. コードを変更する
4. `git add <ファイル> && git commit -m "変更内容"`
5. `gh auth switch --user claude-code-club`（GitHub操作前に必ず切り替え）
6. `git push origin feature/xxx`
7. `git checkout staging && git pull origin staging && git merge feature/xxx && git push origin staging`（stagingへ反映）
8. Railwayのstaging環境（`web-staging-beab.up.railway.app`）が自動デプロイされるのを待ち、実機で確認。直すたびに`feature/xxx`側で修正→再度stagingへmergeを繰り返す
9. 問題なければ `gh pr create --base main --head staging`（検証済みのstagingをそのままmainへ提案）
10. ChatGPTへPRのURLを渡してレビューを依頼
11. Approveをもらったらユーザーが最終承認
12. `gh pr merge <PR番号> --merge`（`--delete-branch` は付けない。stagingは持続的な検証環境用ブランチのため削除してはいけない）
13. `gh auth switch --user iwasegiken`（作業後は必ず戻す）
14. productionのRailway自動デプロイを待ち、本番URL（`web-production-0b8c5f.up.railway.app`）をPC・スマホ両方で確認
15. 不要になった`feature/xxx`はローカル・リモートとも削除してよい（`git branch -d feature/xxx`）

---

## 安全のためのルール

- **`main`へ直接pushしない**。必ず作業ブランチ→staging反映→確認→PR→レビュー→承認→マージの順を守る
- **`staging`は直接開発する場所にしない**。実際のコード変更は必ず`feature/xxx`で行い、検証したい状態がまとまったらstagingへmergeする。stagingは「完成した検証候補を載せる、持続する検証環境」として保つ
- **`staging`ブランチは削除しない**。environment（Railway側のstaging環境）がこのブランチ名と紐付いているため、削除すると次回作業前に作り直しが必要になる（第7回で実際に発生した事故）
- ChatGPTレビューが「条件付きApprove」の場合、本番反映後の実機確認まで済ませてから完了とする
- 秘密情報（APIキー等）はコードに書かず、Railwayの環境変数（production／staging双方）に登録する
- production環境はユーザーが日常的に使うため、stagingで十分確認してからマージする

## 既知の制約（このアプリ固有）

- 依存パッケージはルート`requirements.txt`と`streamlit/requirements.txt`の2箇所に重複しているため、パッケージ追加時は両方を更新する

**解消済み**: 「Railwayのコンテナ再起動（再デプロイ含む）のたびに記録データが消える」問題は、第14回でproduction・staging両環境の`web`サービスに永続ボリューム（マウント先`/app/streamlit/data`）を接続し解消した。詳細は [`本番DB運用.md`](./本番DB運用.md) を参照。
