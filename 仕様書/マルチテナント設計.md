# マルチテナント設計（調査・設計フェーズ）

SaaS本体編 第16回。stagingで稼働中のPostgreSQL（[`保存方式切り替え設計.md`](./保存方式切り替え設計.md)で切り替え済み・実機確認PASS）を土台に、「顧客同士のデータを絶対に混ぜない」ためのテナント分離を設計する。**この文書は調査・設計のみで、まだ実装・commit・push・PR・Railway設定変更・DB変更・Volume削除・production操作は行っていない。**

## 前提（確定事項）

- テナント単位：**世帯＝1テナント**
- 記録の単位：**世帯全体で1つの記録・1つの連続記録**。誰かが食器を洗えば、その世帯のその日の記録として1件カウントする
- 第16回では**認証・個人ユーザー識別を実装しない**（第17回の範囲）
- 将来`records`へ`recorded_by_user_id`を追加し、「誰が洗ったか」を個人単位で記録できる拡張余地を残す。ただし連続記録は世帯単位を基本とする
- productionへはまだ反映しない（staging限定）

## ① テナントIDとその識別方法

- `tenants.id`は**UUID**を採用する（連番IDだと桁の推測・列挙による越境の試みがしやすくなるため、SaaSのテナントIDとしてUUIDを採用するのが一般的な安全側の選択）
- 第16回では個人ログインを作らないため、「今アプリが動いている先はどのテナントか」を**staging環境変数`DEFAULT_TENANT_ID`（UUID文字列）として明示設定**する
- **未設定・空文字・不正なUUID形式の場合はすべてエラー停止する。** コード内への固定値埋め込み、テナントの自動生成、「先頭の1件を自動選択」といったフォールバックは**すべて禁止**する（`保存方式切り替え設計.md`の「`STORAGE_BACKEND`不正値は常にエラー停止し、JSONへ静かにフォールバックしない」という設計方針と同じ考え方をテナントIDにも適用する）

```python
# app.py（イメージ）
import os
import uuid

def get_default_tenant_id():
    raw = os.environ.get("DEFAULT_TENANT_ID", "").strip()
    if not raw:
        raise TenantConfigError("DEFAULT_TENANT_IDが設定されていません。")
    try:
        return uuid.UUID(raw)
    except ValueError as e:
        raise TenantConfigError(f"DEFAULT_TENANT_IDがUUID形式ではありません: {raw!r}") from e

TENANT_ID = get_default_tenant_id()  # 第17回でログインセッション由来の値に差し替え予定
dates = load_dates(tenant_id=TENANT_ID)
```

- `tenant_id`は**`storage.py`から`db.py`へ明示的に渡す**。`storage.py`自身がテナントを決定することはしない（決定するのは呼び出し元の`app.py`）
- `db.py`の公開関数（`load_dates`/`save_dates`/`insert_dates`等、記録のテーブルを操作するすべての関数）は、**`tenant_id`をデフォルト値なしのキーワード専用引数**にする（`def load_dates(conn, *, tenant_id): ...`）。位置引数での呼び出しやデフォルト値での省略を言語レベルで禁止し、呼び忘れば必ず`TypeError`になる

## ② `tenants`テーブルの新設

```sql
CREATE TABLE tenants (
    id          UUID PRIMARY KEY,
    name        TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()

```

- `id`はアプリ側（Pythonの`uuid`標準ライブラリ）で生成する。DB拡張の`pgcrypto`（`gen_random_uuid()`等）は現時点で未導入のため前提にしない（上記調査結果）
- `name`：世帯の表示名（第16回時点では移行時に付与する仮名でよい。例:「初期世帯」。編集UIは第16回では作らない）
- 将来`users`テーブルを追加する際は、`users.tenant_id`で`tenants`を参照させる（1テナント＝N users、第17回）

## ③ `records`への`tenant_id`追加とUNIQUE制約の変更

現状の`records_record_date_unique`は**UNIQUE INDEX**であり（UNIQUE CONSTRAINTではない、上記調査で確認済み）、`db.py`の`ensure_schema()`が`CREATE UNIQUE INDEX IF NOT EXISTS records_record_date_unique ON records (record_date)`で作成したものそのもの。この実際の名前をそのまま使い、決め打ちの別名を使わない。

```sql
DROP INDEX IF EXISTS records_record_date_unique;
CREATE UNIQUE INDEX records_tenant_id_record_date_unique
    ON records (tenant_id, record_date);
```

- 同じ日付でも**テナントが違えば別行として共存できる**（世帯Aと世帯Bが同じ8月31日に記録しても衝突しない）
- 同一テナント内では、引き続き同じ日付を二重登録できない（現行と同じ「1日1件」の意味論を世帯単位で維持）

## ④ 既存の1件を初期世帯テナントへ移す方法（スキーマ移行、順序固定）

stagingには現在1件（`2026-08-31`）のみが存在する。以下の順序で、**1トランザクション内**・**冪等**に実行する`scripts/migrate_to_tenant_schema.py`（新規）を用意する。`保存方式切り替え設計.md②-c`と同じ「書き込み→同一トランザクションで検証→完全一致時のみcommit」の型を踏襲する。

初期世帯のUUIDは、**アプリ側（Pythonスクリプト）で一度だけ生成し、スクリプトの引数・定数として固定**する（`pgcrypto`の`gen_random_uuid()`には依存しない。再実行時も同じUUIDを渡すことで冪等性を保つ）。

```python
INITIAL_TENANT_ID = uuid.UUID("＜固定した初期世帯UUID。実行前に生成し、この値を関係者間で共有・記録する＞")

def migrate_to_tenant_schema(conn=None, initial_tenant_id=INITIAL_TENANT_ID, initial_tenant_name="初期世帯"):
    owns_conn = conn is None
    conn = conn or db.get_connection()
    try:
        before_dates = db.load_dates_legacy(conn)  # tenant_id列がまだ無い時点での読み込み

        with conn.cursor() as cur:
            # 1. tenantsへ初期世帯を冪等に作成(既に存在すれば何もしない)
            cur.execute(
                "INSERT INTO tenants (id, name) VALUES (%s, %s) ON CONFLICT (id) DO NOTHING",
                (initial_tenant_id, initial_tenant_name),
            )
            # 2. recordsへnullableなtenant_id列を追加(既に存在すれば何もしない)
            cur.execute("ALTER TABLE records ADD COLUMN IF NOT EXISTS tenant_id UUID")
            # 3. 既存レコードだけを初期世帯tenant_idでbackfill(NULLの行だけ対象、再実行しても安全)
            cur.execute(
                "UPDATE records SET tenant_id = %s WHERE tenant_id IS NULL",
                (initial_tenant_id,),
            )
            # 4. NULL件数が0であることを確認
            cur.execute("SELECT COUNT(*) FROM records WHERE tenant_id IS NULL")
            null_count = cur.fetchone()[0]
            if null_count != 0:
                raise MigrationVerificationError(f"tenant_id未設定の行が残っています: {null_count}件")

            # 5. 外部キーを追加(既存なら何もしない。制約存在チェックはpg_constraintで行う)
            cur.execute("""
                DO $$ BEGIN
                    IF NOT EXISTS (
                        SELECT 1 FROM pg_constraint
                        WHERE conname = 'records_tenant_id_fkey'
                          AND conrelid = 'records'::regclass
                    ) THEN
                        ALTER TABLE records ADD CONSTRAINT records_tenant_id_fkey
                            FOREIGN KEY (tenant_id) REFERENCES tenants(id);
                    END IF;
                END $$;
            """)
            # 6. tenant_idをNOT NULL化
            cur.execute("ALTER TABLE records ALTER COLUMN tenant_id SET NOT NULL")
            # 7. record_date単独のUNIQUE INDEXを削除
            cur.execute("DROP INDEX IF EXISTS records_record_date_unique")
            # 8. UNIQUE(tenant_id, record_date)を追加
            cur.execute("""
                CREATE UNIQUE INDEX IF NOT EXISTS records_tenant_id_record_date_unique
                ON records (tenant_id, record_date)
            """)

        # 9. 初期世帯の移行前後の日付集合が完全一致することを確認
        after_dates = db.load_dates(conn, tenant_id=initial_tenant_id)
        if after_dates == before_dates:
            conn.commit()  # 10. 完全一致の場合だけcommit
            return {"tenant_id": initial_tenant_id, "match": True}
        else:
            conn.rollback()  # 不一致・例外時はrollback
            raise MigrationVerificationError(
                f"移行後の日付集合が一致しません: 移行前={before_dates}, 移行後={after_dates}"
            )
    except psycopg.Error:
        conn.rollback()
        raise
    finally:
        if owns_conn:
            conn.close()
```

- **1件しかない現時点だからこそ、目視でも確認しやすい**（`railway ssh`から`SELECT * FROM records`して1行だけであることを直接確認できる）。件数が増えてから実施するより今のうちに移行する方が安全
- **再実行しても壊れない**：`ON CONFLICT DO NOTHING`（tenants挿入）、`WHERE tenant_id IS NULL`（backfillはNULLの行だけが対象になり、既に移行済みの行に触れない）、`IF NOT EXISTS`（列・インデックス・DO $$ブロックでの制約存在チェック）により、途中で失敗して再実行しても安全
- 制約名は**すべて実際にDBへ問い合わせて確認した名前**（`records_record_date_unique`）を使う。新しく作る名前（`records_tenant_id_fkey`・`records_tenant_id_record_date_unique`）は本設計内で決め、実装前に改めて`pg_constraint`/`pg_indexes`で衝突がないことを確認する

## ⑤ 第16回で必須とする越境防止の保証（RLSに頼らない設計）

第16回では、次の3点を必須の保証とする。

1. **すべてのSELECT・INSERT・DELETE・同期処理（`save_dates`のような全体置き換え処理を含む）に`tenant_id`条件を付ける**
2. **`tenant_id`を指定しないDB操作をAPI上できなくする**（①のとおり、`db.py`の公開関数は`tenant_id`をデフォルト値なしのキーワード専用引数にする。関数呼び出し自体が成立しないため、レビューやテストで気づく以前に、そもそも実行できない）
3. **顧客A・顧客Bの2テナントを使った越境防止テストを作る**（⑥参照）

```python
# streamlit/db.py（イメージ、tenant_id対応版）
def load_dates(conn, *, tenant_id):
    with conn.cursor() as cur:
        cur.execute(
            "SELECT record_date FROM records WHERE tenant_id = %s",
            (tenant_id,),
        )
        return {row[0].isoformat() for row in cur.fetchall()}


def save_dates(dates, conn, *, tenant_id):
    """tenant_id配下の記録だけを、渡された内容と完全に一致するよう置き換える。
    他テナントの行には一切触れない(WHERE tenant_id = %sを全SQLに付ける)。
    """
    dates = set(dates)
    existing = load_dates(conn, tenant_id=tenant_id)
    to_delete = sorted(existing - dates)
    to_add = sorted(dates - existing)
    with conn.cursor() as cur:
        if to_delete:
            cur.execute(
                "DELETE FROM records WHERE tenant_id = %s AND record_date = ANY(%s::date[])",
                (tenant_id, to_delete),
            )
        if to_add:
            cur.executemany(
                "INSERT INTO records (tenant_id, record_date) VALUES (%s, %s) "
                "ON CONFLICT (tenant_id, record_date) DO NOTHING",
                [(tenant_id, d) for d in to_add],
            )
```

## ⑥ 越境防止テスト（`tests/test_tenant_isolation.py`、新規）

既存の`requires_db`マーカー（`DATABASE_URL`未設定時は自動skip）を踏襲。テナントA・テナントBの2つを作り、テナントAの操作がテナントBのデータへ一切影響しないことを直接確認する。少なくとも次の8項目を確認する。

| # | 検証内容 |
|---|---|
| 1 | テナントAからテナントBの記録を読めない（`load_dates(conn, tenant_id=A)`がBの日付を一切含まない） |
| 2 | テナントAの追加操作（`save_dates`での日付追加）がテナントBへ影響しない |
| 3 | テナントAの削除・取り消し操作がテナントBへ影響しない |
| 4 | テナントAの`save_dates`（全体置き換え・同期処理）が、テナントBの記録を削除しない（Aの置き換えでBの行数・内容が変化しないことを確認） |

## ⑦ RLS（Row Level Security）：第16回は調査・将来設計に留める

### 調査結果（読み取り専用、上記「staging DBの現状」参照）

- アプリが接続するロールは`postgres`で、**`rolsuper=True`かつ`rolbypassrls=True`**。PostgreSQLの仕様上、**スーパーユーザーはRLSを常に完全にバイパスする**（`FORCE ROW LEVEL SECURITY`を付けても無効）。したがって、**現在の接続ロールのままではRLSを有効化しても一切効果がない**
- RLSを実効あるものにするには、①非スーパーユーザーの専用ロールを新規作成し、②そのロール用に別途接続文字列（Railwayの`DATABASE_URL`とは別のRailway環境変数、例:`APP_DATABASE_URL`）を用意し、③アプリの通常操作はそちらで接続する、という構成変更が必要になる。これは**DB操作（ロール作成）とRailway環境変数の追加**を伴うため、本設計の「調査・設計のみ」の範囲を超える
- `pgcrypto`等の拡張は未導入（RLSの前提条件そのものには直接関係しないが、UUID生成をDB側で行う場合は別途検討が必要になる。④のとおり本設計ではDB拡張に依存せずアプリ側でUUIDを生成するため、この点は問題にならない）

### 第16回で行うこと（実装はしない）

- 上記のロール調査結果を設計書に記録する（このセクション）
- **RLSを有効化する場合に必要な非スーパーユーザーロールとポリシー案**を残す：

```sql
-- 第17回以降、実施を判断する場合のイメージ(第16回では実行しない)
CREATE ROLE app_user LOGIN PASSWORD '<Railway側で発行・管理する秘密情報>';
GRANT SELECT, INSERT, UPDATE, DELETE ON records TO app_user;
ALTER TABLE records ENABLE ROW LEVEL SECURITY;
ALTER TABLE records FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON records
    USING (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

- **第17回で「ログインユーザー→世帯メンバーシップ→tenant_id→DBセッション」に接続する案**：ログイン認証ができて初めて「今のリクエストはどのユーザーのものか」が分かり、そのユーザーが所属する世帯（テナント）を特定できる。RLSの`SET app.tenant_id`はリクエストごとに設定する必要があるため、**認証基盤（第17回）とセットでなければ安全に運用できない**。第16回時点で`DEFAULT_TENANT_ID`という固定値運用のままRLSだけ先行導入しても、結局「常に同じテナントIDをSETする」だけになり、実質的な保護効果は⑤のアプリ層の保証と変わらない
- **結論**：第16回ではRLSを実装必須にしない。第16回の保証は⑤（必須の`tenant_id`＋全SQLのテナント条件＋越境防止テスト）を中心とする。RLS導入の可否は、非スーパーユーザーロール作成の実現性も含めて**第17回で実装判断とする**

## ⑨ JSON・PostgreSQLへの切り戻し方針（修正版）

- **初期世帯1テナントだけの段階では、そのtenant_idの記録を抽出して従来形式の`records.json`へ復元できる。**「テナント化後はJSONへ切り戻せない」というのは段階を区別しない言い方で、正確には次のとおり：
  - `scripts/restore_json_from_postgres.py`は、**recordsが`tenant_id`列を持つかどうかで挙動を切り替える新旧互換の設計**にする（Stage 1で実装済み）。移行期間中、tenant_id必須のコードだけが先にstagingへデプロイされ、DB移行（`migrate_to_tenant_schema.py`実行）がまだの状態になる瞬間があるため、その間も緊急JSON復元手段を失わないようにする
    - `tenant_id`列がまだ無い旧スキーマ：従来どおり全recordsを復元する。`tenant_id`を指定した場合はエラー停止する（旧スキーマにテナントの概念はまだ存在しないため）
    - `tenant_id`列がある新スキーマ：`tenant_id`の指定を必須とする。未指定・不正なUUIDではエラー停止し、**全テナントを暗黙に混ぜてJSONへ書き出すことは絶対にしない**
  - 初期世帯1件だけの現状であれば、その`tenant_id`を指定して復元すれば、移行前と同じ内容の`records.json`が得られる
- **複数テナント運用が始まった後は、単一の`records.json`では全テナント分を保持できない**ため、**JSONへの全面切り戻しは禁止する**（1テナント分だけを指定して部分的にJSONへ書き出すことはできても、それは「全面切り戻し」ではなく「特定世帯のためのエクスポート」であり、アプリ全体の保存方式を`STORAGE_BACKEND=json`へ戻すこととは区別する）
- **スキーマ変更前にDBバックアップ（⑧手順2のダンプ）を取得**し、基本の切り戻しは「コードとDBスキーマのロールバック」とする（`tenant_id`列・複合UNIQUE・`tenants`テーブル導入前のリビジョンへコードを戻し、必要ならダンプからスキーマを復元する）
- Volumeや既存JSON（`web-volume-lbdR`）は**今回削除しない**

## ⑩ 同時更新に関する制約（新規、明記のみ）

現在の`save_dates`（`storage.py`/`db.py`とも）は「**日付集合全体を読み込み→差分計算→置き換え**」という方式である。世帯＝1テナントとなり、将来同じ世帯の複数人（複数端末）が**ほぼ同時に**記録・取り消しを行うと、後から書き込んだ側が先に書き込んだ側の変更を上書きしてしまう**ロスト・アップデート**が起こり得る（例：2人が同時に別の日を追加しようとすると、片方の追加が消える可能性がある）。

- **この制約は第16回の設計として明記するに留め、実装は次のとおり判断する**：
  - 記録の追加・取り消し（1日単位の操作）は、`db.py`に**`tenant_id`付きの原子的なINSERT／DELETE**（1行単位、`保存方式切り替え設計.md`の`insert_dates`と同様の考え方）を追加し、`app.py`の記録・取り消しボタンの処理を「全体を置き換える`save_dates`」ではなく、この原子的な1行操作へ寄せる。**この改修は第16回のうちに実施する**（`db.py`への追加のみで完結し、新たな設計判断を要しないため）
  - ただし、これは「ほぼ同時の別日操作」によるロスト・アップデートを防ぐものであり、**「同じ日付への完全な同時二重送信」のような真の競合状態を排完全に除するものではない**（そのためには楽観ロック・DBアドバイザリロック等が必要）。**完全な同時実行保証は第16回では行わず、必要になった時点で第17回以降に判断する**

---

## ⑪ 将来の`users`／`recorded_by_user_id`追加余地

```sql
-- 第17回で追加予定（第16回では作らない）
CREATE TABLE users (
    id          UUID PRIMARY KEY,
    tenant_id   UUID NOT NULL REFERENCES tenants(id),
    name        TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE records ADD COLUMN recorded_by_user_id UUID REFERENCES users(id);  -- NULL許容
```

- `recorded_by_user_id`は**NULL許容**にする：世帯単位の記録・連続記録という現行の意味論を壊さずに、「誰が洗ったか」を分かる範囲でだけ付加情報として持たせられる
- 連続記録・最長記録の計算（`calc_current_streak`/`calc_best_streak`）は引き続き**テナント単位の日付集合**に対して行う（変更不要）
- テナント境界（`tenant_id`）を作り直す必要は一切ない
