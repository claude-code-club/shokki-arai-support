# トラブル復旧ガイド（reset / revert / reflog / stash・本番ロールバック）

Git×Railway上級マスター応用編 第10回「やらかしても戻せる」のまとめ。

---

## ① やらかし→復旧の記録（実演）

`practice/recovery-drill`というローカル限定の練習ブランチ（mainには一度も合流させず、練習後に削除済み）で、4つの技を実際に体験した。

### resetの練習（まだ誰にも共有していないコミット）
1. `app.py`に不要な走り書きをコミット（`やらかしコミット: テスト用のメモをapp.pyに書いてしまった`）
2. `git reset --hard HEAD~1` で、そのコミットごと無かったことにした
3. → **pushする前の失敗は、resetで最も簡単に消せる**

### revertの練習（共有済みだったと仮定した変更）
1. 間違った変更をコミット（`やらかしコミット2: push済みだったと仮定した間違い`）
2. `git revert --no-edit <コミットID>` で、打ち消しコミットを作成
3. 履歴には「間違い」も「打ち消し」も両方残る（＝**誰が見ても何が起きたか追える**）
4. → **共有済みの変更は、履歴を消さないrevertで戻す**

### reflogの練習（"消えた"コミットの救出）
1. 大事なつもりのコミット（`大事な作業(のつもり)`）を作成
2. うっかり`git reset --hard HEAD~2`し、`git log`から2コミット分が見えなくなった
3. `git reflog` で操作履歴を確認 → 「消えた」コミットのIDが残っていた
4. `git reset --hard <見つけたコミットID>` で復元成功
5. → **reflogは自分のローカル操作の記録。resetし過ぎても大抵は救える**

### stashの練習（作業中の変更を一時退避）
1. コミットしていない作業中の変更がある状態で、別ブランチに移動したくなった
2. `git stash push -m "作業中の一時退避"` で退避 → 作業ツリーがクリーンになりブランチ移動が可能に
3. 元のブランチに戻って `git stash pop` → 退避した変更が復元
4. → **コミットするほどでもない作業を、他の作業のために一時的にどける**

## ② 使い分け表（このSaaSでの判断基準）

| 状況 | 使う技 | 理由 |
|---|---|---|
| コミットしたが、まだpushしていない間違い | `reset` | 誰にも見られていないので、消してしまってよい |
| pushして共有済みの間違い（PR中・main反映後など） | `revert` | 履歴を書き換えず、打ち消しコミットで安全に取り消す |
| 「消した」「戻しすぎた」と焦ったとき | `reflog` | だいたいのローカル操作はreflogに残っており、パニックにならず確認できる |
| コミットするほどでもない作業中の変更を、一旦どけたい | `stash` | 作業ツリーをクリアして、他のブランチ作業や緊急対応に移れる |

## ③ 本番（Railway）ロールバック手順

Railwayは各デプロイの履歴（Deployments画面のHISTORY欄）を保持しており、過去の成功したデプロイへワンクリックで戻せる。

1. Railwayのサービス画面 → 「Deployments」タブを開く
2. HISTORY一覧から、**戻したい直前の「成功していたデプロイ」**を探す
3. そのデプロイ行の「⋮」（三点リーダー）メニューを開く
4. 「Redeploy」を選択 → そのコミット時点のビルドが再度production環境にデプロイされる

**注意点**
- Railwayのロールバックは「そのコミット時点の状態を再デプロイする」であり、Gitの履歴（GitHub側）は変わらない。根本原因はGit側で別途`revert`して直す必要がある
- ロールバック後、mainブランチの最新コミットと本番の状態が一致しなくなるため、原因を修正したら改めてmainへ反映し、本番を最新に追いつかせる
