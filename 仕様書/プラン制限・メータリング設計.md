# プラン制限・メータリング設計（第20回: プラン制限とメータリング）

## ①目的・範囲

第18回（Stripeサブスク決済）・第19回（継続課金・Webhook）で、世帯（tenant）単位の
Free/Standard契約状態を管理できるようになった。第20回では、この契約状態を実際の
機能制限へ結び付ける。

- 「30日間の詳細分析」をStandard限定機能として追加する
- 「今月の振り返り」を新設し、Freeは世帯につき月3回まで、Standardは無制限とする
- Freeの上限到達時に、現在の使用回数とStandardへのアップグレード導線を表示する

日々の「食器洗い記録の追加・取り消し・連続記録表示」は、第20回の変更によって
一切制限されない（既存のFree/Standardどちらの世帯でも従来どおり無制限に使える）。
アプリの中心機能を有料化して使えなくする変更は行わない。

Stripeテストモード（Sandbox）限定。production・mainには一切触れない。

## ②既存スキーマとの照合

必要な情報は次の2種類。

1. 「この世帯はStandardの機能を使えるか」→ 第18回で作った`tenant_subscriptions`
   （`plan`・`status`）で既に判定可能。新しい列・テーブルは不要
2. 「この世帯は今月、この機能を何回使ったか」→ 既存スキーマには存在しない。
   新しいテーブル（`tenant_usage`）が必要

## ③Standard判定（既存ロジックの再利用、新設しない）

第19回の`customer.subscription.updated`ハンドラは、次の判定で`plan`を決めている
（`streamlit/webhook.py`）。

```python
plan = "standard" if status in billing._ACTIVE_SUBSCRIPTION_STATUSES else "free"
```

第20回でも、この`_ACTIVE_SUBSCRIPTION_STATUSES = ("active", "trialing")`をそのまま
再利用し、次の1関数に集約する（`streamlit/billing.py`に追加）。

```python
def has_standard_access(plan_status):
    return (
        plan_status["plan"] == "standard"
        and plan_status["status"] in _ACTIVE_SUBSCRIPTION_STATUSES
    )
```

- `plan="standard"`かつ`status`が有効（`active`/`trialing`）のときだけStandard機能を許可する
- `status="past_due"`（支払い失敗中）は、`plan`列自体は`"standard"`のまま残るが
  （第19回の`invoice.payment_failed`ハンドラの仕様）、`_ACTIVE_SUBSCRIPTION_STATUSES`に
  含まれないため`has_standard_access()`は`False`を返す。**別の判定を新設せず、
  支払いが正常に戻る（Webhookで`status`が`active`へ戻る）までFree相当の制限を適用する**
- `plan_status`の取得自体に失敗した場合（DB障害等）は、呼び出し元が例外を受け取り、
  Standardと判定せず機能を閉じる（fail closed、④参照）

## ④DB設計

```sql
CREATE TABLE IF NOT EXISTS tenant_usage (
    tenant_id    UUID NOT NULL REFERENCES tenants(id),
    metric_key   TEXT NOT NULL,
    period_start DATE NOT NULL,
    usage_count  INTEGER NOT NULL DEFAULT 0,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, metric_key, period_start)
)
```

- `PRIMARY KEY (tenant_id, metric_key, period_start)`により、指定されたUNIQUE制約を
  そのまま満たす
- `tenant_id`は`tenants(id)`への外部キー（未知の世帯の行を作れない）
- `period_start`は「日本時間(Asia/Tokyo)でのその月の1日」を表す`DATE`値
  （例: 2026年9月なら`2026-09-01`）。`DATE`型自体はタイムゾーンを持たないため、
  日本時間で計算した暦月をそのままキーにする。`created_at`/`updated_at`は
  `TIMESTAMPTZ`のままとし、PostgreSQLが内部的にUTCで保持する（既存の他テーブルと
  同じ方針）
- 月が変わると`period_start`の値そのものが変わるため、新しい行が作られ
  `usage_count`は自然に0から始まる（明示的なリセット処理は不要）

## ⑤原子的な上限判定・加算（読み込み→加算→保存を使わない）

「読み込み→Pythonで加算→保存」は、2つのリクエストがほぼ同時に来た場合に
上限を超えて加算されうる（レースコンディション）。第18回の
`upsert_subscription_if_new_session()`と同じ考え方で、1回のSQL文だけで
「上限未満なら加算、上限以上なら何もしない」を原子的に行う。

```sql
INSERT INTO tenant_usage (tenant_id, metric_key, period_start, usage_count, updated_at)
VALUES (%(tenant_id)s, %(metric_key)s, %(period_start)s, 1, now())
ON CONFLICT (tenant_id, metric_key, period_start) DO UPDATE SET
    usage_count = tenant_usage.usage_count + 1,
    updated_at = now()
WHERE %(limit)s IS NULL OR tenant_usage.usage_count < %(limit)s
RETURNING usage_count
```

- 行がまだ無い場合（今月初めての利用）は無条件で`usage_count=1`として挿入される
- 既に行がある場合、`usage_count < limit`のときだけ`DO UPDATE`が実際に適用され、
  加算後の値が`RETURNING`される。上限に達していれば`DO UPDATE`のWHERE条件が
  偽になり、更新は行われず`RETURNING`は空になる（PostgreSQLの
  `INSERT ... ON CONFLICT DO UPDATE ... WHERE`の標準的な挙動）
- 呼び出し側は「`RETURNING`が空だったか」だけを見て、上限到達を判定する
  （加算できた場合は加算後の回数、できなかった場合は`None`を返す）
- `limit=None`を渡すとStandard（無制限）として扱う。Free/Standardで別のSQLを
  用意せず、同じ関数・同じSQL文を共用する
- 行レベルロックにより、同時に複数のリクエストが来ても`usage_count`が
  上限を超えて加算されることはない（Streamlitの再実行・二重クリックによる
  重複加算もこの仕組みで安全側に倒れる）

## ⑥「30日間の詳細分析」（Standard限定・使用回数制限なし）

こちらは月間の回数制限ではなく、「Standard契約かどうか」だけを問う単純なゲートで
ある。`has_standard_access()`が`False`の世帯には、分析内容そのものを一切送信せず
（サーバー側で計算しない）、鍵アイコンとアップグレード案内だけを表示する。

## ⑦「今月の振り返り」（月間3回まで、Standardは無制限）

- `metric_key = "monthly_reflection"`
- Freeの上限: 3回/月
- ボタン押下時、`has_standard_access()`を確認したうえで⑤の原子的加算を実行する。
  Standardは`limit=None`、Freeは`limit=3`で同じ関数を呼ぶ
- 上限に達している場合、`UsageLimitExceededError`を送出し、DBへは一切書き込まない
  （加算できなかったことと、コンテンツを表示しないことが1つの判定で一致する）
- 画面には、現在の使用回数（Free時のみ）・上限到達時のアップグレード案内を表示する

## ⑧アップグレード導線（既存のStripe Checkout導線を再利用）

第18回で実装済みの`billing.start_checkout_session()`をそのまま呼び出す。新しい
Checkout Session作成ロジックは作らない。呼び出し元（app.py）を「プラン」欄・
「30日間の詳細分析」の鍵表示・「今月の振り返り」の上限到達表示、の3箇所に増やす
だけで、admin限定の権限チェック（`role != "admin"`ならPermissionDeniedError）は
`billing.py`側に既に存在するものをそのまま利用する。memberには、これら3箇所とも
購入ボタン自体を表示しない（UI側の分岐は`USER_ROLE == "admin"`を条件にする、
第17回の`世帯の設定(admin専用)`と同じパターン）。

## ⑨障害時の安全側動作（fail closed）

- DB接続・クエリが失敗した場合、Standard判定・使用回数取得のいずれも例外を
  送出する（`MeteringUnavailableError`）。呼び出し元（app.py）は、この例外を
  「Standardではない」「使用不可」として扱い、有料機能を一切開放しない
- Stripe側の状態取得（`billing.fetch_plan_status`）が失敗した場合も同様に
  Standardと判定しない

## ⑩他世帯からの分離

`tenant_usage`のすべての操作は`tenant_id`をWHERE条件・複合主キーに含むため、
他世帯の使用量を読み書きすることは構造的にできない（第16回のrecordsテーブル、
第18回のtenant_subscriptionsと同じ設計方針）。

## ⑪モジュール構成

- `streamlit/billing.py`：`has_standard_access()`を追加（既存の
  `_ACTIVE_SUBSCRIPTION_STATUSES`を再利用するだけの薄い関数）
- `streamlit/metering.py`（新設）：`tenant_usage`に関する原子的な加算・取得、
  「今月の振り返り」固有のFree上限（3回）定数、app.pyから呼ぶ入口
  （DB接続を自前で管理するラッパー、`billing.py`の`fetch_plan_status`等と
  同じパターン）
- `streamlit/app.py`：契約判定・上限判定のロジックは持たず、`billing`/`metering`
  が返した結果を表示するだけに留める

## ⑫Free/Standard/past_due等の利用可否表

| 状態 | 日々の記録機能 | 30日間の詳細分析 | 今月の振り返り |
|---|---|---|---|
| Free（未契約） | ○ 無制限 | ✕（鍵表示＋アップグレード案内） | ○ 月3回まで |
| Standard（`status=active`/`trialing`） | ○ 無制限 | ○ | ○ 無制限 |
| `status=past_due`（支払い失敗中） | ○ 無制限 | ✕（Free相当） | ○ 月3回まで（Free相当） |
| `status=canceled`（解約済み、`plan=free`） | ○ 無制限 | ✕ | ○ 月3回まで |
| プラン状態の取得に失敗（DB障害等） | ○ 無制限（記録機能自体は本設計の対象外） | ✕（fail closed） | ✕（利用状況を表示せず、加算もしない） |

## ⑬テスト方針

- `has_standard_access()`：plan/statusの組み合わせごとの単体テスト（DB不要）
- `tenant_usage`の原子的加算：Free上限到達（3回まで成功・4回目は失敗）、
  Standard無制限、他世帯への非干渉、月が変わると0から始まることをDB接続テストで確認
- 障害時にfail closedとなること（DB未設定時に例外が伝播し、許可を返さないこと）
