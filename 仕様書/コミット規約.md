## ① 今の歴史の診断

`git log --oneline`で全履歴（PRマージ含め約23コミット）を確認した結果。

**良い点**
- ほぼ全てのコミットが1つの意味のある単位になっている（「色々直した」のような曖昧な一括りは無し）
- 日本語で「何を・なぜ変えたか」がその場で読み取れるメッセージが多い

**粗さが残る点**
1. `応援コメントのモデルIDを修正し、失敗時のエラーをログに残すよう変更`（3e89536）
   → **1つのコミットに「不具合修正」と「観測性の改善」という2つの意味が混ざっている**。本来は2コミットに分けるべきだった例。
2. 型（prefix）の統一が無く、`〜を追加`／`〜を修正`／`〜に記録`のように文体がまちまちで、ぱっと見て「機能追加なのか修正なのかドキュメントなのか」が分からない
3. `食器洗いサポート 初回公開`（e239731）は初回コミットとして許容範囲だが、何が含まれるか（MVP機能一覧など）までは書かれていない

## ② コミットメッセージの型（規約）

```
<type>: <何を・なぜ変えたか、1行で>

（必要であれば、空行を挟んで詳細説明）
```

**type一覧**

| type | 意味 |
|---|---|
| `feat` | 新しい機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | ドキュメントのみの変更 |
| `chore` | 動作に影響しない雑務（設定・依存関係・ログ追加など） |
| `refactor` | 動作を変えないコードの整理 |

### 書き直し例（Before → After）

| Before（実際のコミット） | After（規約に沿った書き方） |
|---|---|
| `Railway本番デプロイ用の設定ファイルを追加(Procfile/requirements.txt)` | `feat: Railway本番デプロイ用の設定ファイルを追加(Procfile/requirements.txt)` |
| `Railwayビルド失敗を修正: ルートrequirements.txtの間接参照をやめ直接記載に変更` | `fix: Railwayビルド失敗を解消(requirements.txtの間接参照を直接記載に変更)` |
| `応援コメントのモデルIDを修正し、失敗時のエラーをログに残すよう変更` | `fix: 応援コメントのモデルIDを修正`<br>＋別コミット`chore: Claude API失敗時にエラーをログへ出力するよう追加`（本来2コミットに分割すべきだった例） |
| `8月花火イラスト刷新を基準.mdに記録` | `docs: 8月花火イラスト刷新の内容を基準.mdに記録` |

## ③ マージとリベースの使い分け

**マージ（merge）** ＝ 2本のブランチの歴史を、そのまま合流させる。分岐した事実も残る。
**リベース（rebase）** ＝ 自分のブランチの土台を、最新のmainに"付け替える"。分岐前の歴史を書き換えて一直線にする。

このプロジェクトでは、PR #1〜#8まで**すべてマージ**（`gh pr merge --merge`）を使ってきた。理由：

- PRはすでにGitHubへpush済み＝**共有された歴史**。共有済みの歴史を書き換えるリベースは危険（安全メモの通り）
- コンフリクト解消PR(#2)のように「A案／B案／統合解消」という**経緯そのものに価値がある**場合、マージなら3コミットとも残るが、リベース＋squashだと経緯が1つに潰れて読めなくなる

**リベースが向いているケース（今回は未使用）**：
- **まだpushしていない、自分だけのローカル作業ブランチ**で、「保存のための細かいコミット」を1〜2個のきれいなコミットにまとめてからPRを出したいとき（`git rebase -i`でのsquash）

**このSaaSでの結論**：PRを出す前のローカル整理にはリベースを検討してよいが、**pushした後・PRを作った後は絶対にリベースしない（マージのみ）**。これがこのプロジェクトの方針。
