# main保護の設定とレビュー基準（第11回）

Git×Railway上級マスター応用編 第11回「mainを仕組みで守る」のまとめ。

---

## ① main保護（protected branch）の設定内容

GitHub APIで`main`ブランチに以下を設定した。

| 項目 | 設定 | 意味 |
|---|---|---|
| Require pull request before merging | 有効（承認0件、1人開発中のため） | mainへの変更は必ずPR経由。直pushは不可 |
| Require status checks to pass | 有効（`test`必須） | CIが失敗している間はマージできない（第12回で追加） |
| Enforce for administrators | **有効** | リポジトリ管理者(claude-code-club)自身も例外なくルールに従う |
| Allow force pushes | 無効 | mainの履歴を書き換えるforce pushを禁止 |
| Allow deletions | 無効 | mainブランチ自体の削除を禁止 |

### 設定の反省と修正（重要な学び）

最初`enforce_admins`を`false`で設定したところ、管理者アカウントでの直pushが**「Bypassed rule violations」という警告付きで成功してしまった**。「直push禁止」という要求を満たしていなかったため、`enforce_admins`を`true`に変更し、再度直pushを試みたところ、今度は`GH006: Protected branch update failed`で完全にブロックされることを確認した。

**設定した"つもり"と、実際に効いているかは別**——実際に直pushを試して検証するところまでやって初めて「保護できている」と言える、という教訓。

### 唯一人開発における運用方針

`--admin`（管理者権限による保護ルールの明示的バイパス）は、**通常運用では使用しない**。`enforce_admins`を有効にした意味（管理者も例外なくルールに従う）と矛盾するため。

1人開発中の現在は、以下で運用を統一する。

- PR経由でのマージ: 必須
- CI（`test`ジョブ）の成功: 必須
- `enforce_admins`: 有効
- 必須承認レビュー数(`required_approving_review_count`): **現在は0件**
- 共同開発者が参加した時点で、承認レビュー数を**1件へ変更**する
- ChatGPTレビューは、設計・実装内容に対する承認として記録するが、GitHub上の正式な「Approve」とは別のものとして扱う
- `--admin`によるルール回避は、緊急時などやむを得ない場合を除き使用しない

## ② レビュー基準・コメントの型

### 何を見るか（レビューチェックリスト）

1. **目的との一致**: このPRは何を解決しようとしていて、差分はその目的に対して過不足ないか
2. **影響範囲**: 変更が意図しない箇所（他の機能・データ構造）に波及していないか
3. **安全性**: 秘密情報の直書き、危険な削除・上書き操作が無いか
4. **動作確認**: staging等での実機確認が伴っているか、テストはあるか
5. **今後への影響**: 依存関係の重複など、将来の保守コストが増える判断は明記されているか

### コメントの型（良い点＋提案）

```
👍 良い点: （具体的に何が良いか）
💡 提案: （こうするともっと良くなる、という前向きな言い方。命令や詰問にしない）
```

例:
> 👍 良い点: モデルID修正と合わせてエラーログを残す変更が入っており、次に同じ不具合が起きても原因調査がしやすくなっている。
> 💡 提案: 今回は1コミットに2つの意図が混ざっているので、次回は分けるとレビューがしやすいかもしれません。

## ③ なぜmain保護・必須レビューが実務で必要か

- **人は疲れる・急いでいるとミスをする**。「気をつける」は仕組みではないので、いつか必ず抜ける
- **本番SaaSは"止まらない・壊れない"が信頼そのもの**。直pushでmainが壊れると、利用者に即座に影響する
- **1人開発でも意味がある**理由：
  - 未来の自分は、今の自分より文脈を覚えていない「他人」に近い。PRという形で差分と理由を残すことは、未来の自分へのレビューでもある
  - チームが増えたときに、突然ルールを敷き直す必要がない（最初から仕組みがある状態を保てる）
  - 直push可能な状態は「うっかり」の入口を常に開けたままにする、ということでもある
