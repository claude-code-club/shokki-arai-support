# 保存方式（JSON／PostgreSQL）切り替え 設計（調査・設計フェーズ）

`app.py`が実際にPostgreSQLを読み書きできるようにするための設計。**この文書は設計のみで、まだ実装・commit・Railway設定変更は行っていない。**

---

## ① 切り替えの判断基準：`DATABASE_URL`の有無ではなく`STORAGE_BACKEND`の明示指定

現状の`db.py`は`DATABASE_URL`環境変数の有無で動作を決める設計だが、**これをアプリの保存先切り替えの判断基準にはしない**。

- `DATABASE_URL`は「接続先が分かっている」ことしか意味しない。将来、他の目的でproductionにも`DATABASE_URL`が存在するようになった場合、意図せずproductionの保存先までPostgreSQLへ切り替わってしまう事故になり得る
- 代わりに、**新しい環境変数`STORAGE_BACKEND`**（値: `json`｜`postgres`、未設定時のデフォルトは`json`）を導入し、これだけを保存方式の判断基準にする
- **stagingの`web`サービスにだけ`STORAGE_BACKEND=postgres`を設定**し、productionには設定しない（＝productionは何もしなくても自動的にJSON保存のまま維持される）

---

## ② `streamlit/storage.py`の新設（切り替えの単一窓口）

`app.py`が呼ぶ関数を`logic`から`storage`へ差し替えるだけで完結するよう、間に薄い選択レイヤーを挟む。

```python
"""保存方式(JSON / PostgreSQL)を、環境変数STORAGE_BACKENDで明示的に切り替える。

DATABASE_URLの有無ではなくSTORAGE_BACKENDの値だけで判断する。
PostgreSQL障害時にJSONへ自動フォールバックすることは行わない
(二重管理・データ不整合を避けるため。障害時は例外を送出し、app.py側で
 エラー表示してst.stop()する、既存のRecordsFileCorruptedError処理と同じ扱いにする)。
"""

import os

import psycopg

import db
import logic
from logic import RecordsFileCorruptedError  # noqa: F401 (app.pyから再利用)

STORAGE_BACKEND_ENV = "STORAGE_BACKEND"
VALID_BACKENDS = ("json", "postgres")


class StorageConfigError(Exception):
    """STORAGE_BACKENDの値が不正、またはpostgres指定なのにDATABASE_URL未設定の場合。"""


class StorageUnavailableError(Exception):
    """PostgreSQLへの接続・読み書きに失敗した場合。JSONへは自動フォールバックしない。"""


def get_backend_name():
    backend = os.environ.get(STORAGE_BACKEND_ENV, "json").strip().lower()
    if backend not in VALID_BACKENDS:
        raise StorageConfigError(
            f"{STORAGE_BACKEND_ENV}の値が不正です: {backend!r}（json または postgres）"
        )
    if backend == "postgres" and not db.is_configured():
        raise StorageConfigError(
            "STORAGE_BACKEND=postgres が指定されていますが、DATABASE_URLが設定されていません。"
        )
    return backend


def load_dates():
    if get_backend_name() == "json":
        return logic.load_dates()
    try:
        conn = db.get_connection()
    except db.DatabaseNotConfiguredError as e:
        raise StorageConfigError(str(e)) from e
    try:
        db.ensure_schema(conn)
        result = db.load_dates(conn)
        conn.commit()  # ensure_schemaのDDLを確定させ、開いたトランザクションを綺麗に終える
        return result
    except psycopg.Error as e:
        conn.rollback()
        raise StorageUnavailableError(f"PostgreSQLへの接続・読み込みに失敗しました: {e}") from e
    finally:
        conn.close()


def save_dates(dates):
    if get_backend_name() == "json":
        logic.save_dates(dates)
        return
    try:
        conn = db.get_connection()
    except db.DatabaseNotConfiguredError as e:
        raise StorageConfigError(str(e)) from e
    try:
        db.ensure_schema(conn)
        db.save_dates(dates, conn=conn)  # db.pyはSQL操作のみ。commitはここでstorage.pyが行う
        conn.commit()
    except psycopg.Error as e:
        conn.rollback()
        raise StorageUnavailableError(f"PostgreSQLへの書き込みに失敗しました: {e}") from e
    finally:
        conn.close()
```

- `logic.load_dates`/`logic.save_dates`（JSON、引数なしのデフォルト呼び出し）と、`db.load_dates`/`db.save_dates`（PostgreSQL、`conn`必須）の**呼び出し方の違いをここで吸収**する
- `today_jst`・`calc_current_streak`・`calc_best_streak`・`build_month_progress`など、保存方式に依存しない純粋な集計関数は引き続き`logic`から直接importする（変更不要）

### ②-a `STORAGE_BACKEND`の不正値は必ずエラー停止し、JSONへは戻さない

`get_backend_name()`は次の2パターンでのみ`StorageConfigError`を送出する。**いずれの場合も`json`へフォールバックすることはなく、呼び出し元（`app.py`）でエラー表示・`st.stop()`し、処理を止める。**

- `STORAGE_BACKEND`に`json`・`postgres`以外の値が設定されている場合（例: 誤って`Postgres`・`POSTGRESQL`・`pg`などタイプミスした場合。大文字小文字は正規化して比較するが、それでも一致しない値はすべて不正値として扱う）
- `STORAGE_BACKEND=postgres`が指定されているが`DATABASE_URL`が設定されていない場合（設定漏れ）

これにより、「設定ミスに気づかずJSONで動き続けてしまい、実はPostgreSQLへ切り替わっていなかった」という**静かな設定ミス**を防ぐ。未設定（環境変数が存在しないこと自体）だけが唯一`json`扱いになる正当なケースであり、それ以外の「値はあるが不正」なケースはすべて明示的にエラーにする。

### ②-b PostgreSQL接続のcommit・rollback・close管理

**`db.py`はSQL操作のみを行い、`commit`・`rollback`は一切呼ばない。** トランザクションの確定・取消の判断は、必ず呼び出し元（`storage.py`、または`migrate_to_postgres.py`）が行う。理由は、移行スクリプトで「書き込み→照合」を1つのトランザクションにまとめ、**照合が一致した場合だけ確定する**ようにするため（`db.py`自身が書き込み直後に`commit`してしまうと、後続の照合で不一致が見つかっても、書き込みだけ先に確定してしまう）。

```python
def ensure_schema(conn):
    """recordsテーブルが無ければ作成する(SQL操作のみ、commitしない)。"""
    with conn.cursor() as cur:
        cur.execute(
            """
            CREATE TABLE IF NOT EXISTS records (
                id          BIGSERIAL PRIMARY KEY,
                record_date DATE NOT NULL,
                created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
            )
            """
        )
        cur.execute(
            """
            CREATE UNIQUE INDEX IF NOT EXISTS records_record_date_unique
            ON records (record_date)
            """
        )
    # commitしない。呼び出し元がトランザクション境界を制御する。


def insert_dates(dates, conn):
    """与えた日付集合を追加する(SQL操作のみ、commit・rollbackは呼び出し元の責任)。"""
    with conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO records (record_date) VALUES (%s) ON CONFLICT (record_date) DO NOTHING",
            [(d,) for d in sorted(dates)],
        )


def save_dates(dates, conn):
    """記録日の集合を、渡された内容と完全に一致するよう置き換える(SQL操作のみ)。"""
    dates = set(dates)
    existing = load_dates(conn)
    to_delete = sorted(existing - dates)
    to_add = sorted(dates - existing)
    with conn.cursor() as cur:
        if to_delete:
            cur.execute(
                "DELETE FROM records WHERE record_date = ANY(%s::date[])",
                (to_delete,),
            )
        if to_add:
            cur.executemany(
                "INSERT INTO records (record_date) VALUES (%s) ON CONFLICT (record_date) DO NOTHING",
                [(d,) for d in to_add],
            )
```

**責任分担のまとめ**:

| 層 | 責任 |
|---|---|
| `db.py` | SQL操作のみを行う。`commit`・`rollback`は一切呼ばない |
| `storage.py` | アプリからの通常操作について、接続取得・`db.py`の呼び出し・**正常終了時のみ`commit()`**・例外発生時は`rollback()`・`finally`での`close()`保証、をすべて担う |
| `migrate_to_postgres.py` | JSON→DBの書き込み（`insert_dates`）と、日付集合の完全一致照合（`load_dates`での再読み込み・比較）を**同一トランザクション内**で行う。完全一致した場合だけ`commit()`し、**不一致または例外時は`rollback()`して書き込みを確定させない** |
| `restore_json_from_postgres.py` | 読み取り専用。`db.load_dates(conn)`の後、接続を必ず`close()`する。データを変更しないため`commit`/`rollback`は不要だが、`close()`は必須 |

同一トランザクション内で、`insert_dates`（未コミット）の直後に`load_dates`で読み直しても、**自分自身が書いた未コミットの変更は同じトランザクション内では見える**（read-your-own-writes、PostgreSQLの標準的な挙動）ため、「書き込み→同一トランザクションで照合→一致すればcommit、不一致ならrollback」が正しく機能する。

### ②-c `migrate_to_postgres.py`の改修（書き込みと照合を同一トランザクションに）

```python
def migrate(data_file=None, conn=None):
    data_file = data_file or logic.DATA_FILE
    json_dates = logic.load_dates(data_file=data_file)

    owns_conn = conn is None
    conn = conn or db.get_connection()
    try:
        db.ensure_schema(conn)
        db.insert_dates(json_dates, conn=conn)   # まだcommitしない
        db_dates = db.load_dates(conn)            # 同一トランザクション内なので未コミット分も見える
        result = db.compare_date_sets(json_dates, db_dates)
        if result["match"]:
            conn.commit()                          # 完全一致した場合だけ確定
        else:
            conn.rollback()                        # 不一致ならこの移行によるINSERTを取り消す
            raise MigrationVerificationError(
                f"移行後の日付集合が一致しません: "
                f"JSONのみ={result['only_in_json']}, DBのみ={result['only_in_db']}"
            )
        return result
    except psycopg.Error:
        conn.rollback()
        raise
    finally:
        if owns_conn:
            conn.close()
```

**変更点**: 従来案では`db.insert_dates`が自分で`commit`していたため、照合で不一致が見つかっても書き込みは既に確定してしまっていた。改修後は、`insert_dates`はSQLを実行するだけで確定させず、**同一トランザクション内で照合まで行い、完全一致した場合のみ`commit`、不一致・例外時は`rollback`**する。これにより、「不一致のまま中途半端なデータがDBに残る」事故を防ぐ。

### ②-d `restore_json_from_postgres.py`（変更なし、接続close確認のみ）

読み取り専用のため、この処理自体は元の設計から変更しない。`db.load_dates(conn)`のあと、`finally`で確実に`conn.close()`すること、JSON書き戻し前に`logic.backup_data()`で既存`records.json`を退避する手順、はそのまま維持する。

## ⑦ 「stagingのJSON用Volume（`web-volume-lbdR`）を将来外せるか」の条件とリスク

現在、プロジェクト全体のVolumeがTrial Planの上限（3つ）に達しており、production用PostgreSQLを追加するには、staging側のJSON用Volumeを将来的に外して枠を空ける、という選択肢が考えられる。**今回は削除しない。** 条件とリスクを整理する。

### 外してよいと判断するための条件（すべて満たすこと）

- [ ] `STORAGE_BACKEND=postgres`でstagingが**安定して一定期間**（例: 数日〜1週間程度）稼働し、記録・取り消し・表示のすべてが問題なく動いていること
- [ ] アプリ内のどの機能も、もはや`logic.py`のJSON I/Oを経由していないこと（`storage.py`経由に統一されていること。コードレビューで確認）
- [ ] Volume削除前に、**最終スナップショットとして`records.json`と`backups/`を`railway volume files download`でGitリポジトリ外・operator本人のPCへ退避**しておくこと（Volumeを削除するとRailway上のデータは復元不能になるため、監査・万一の参照用に残す）
- [ ] PostgreSQL側にも、削除前時点のバックアップ手段（Railwayの日次バックアップ機能、または`pg_dump`等）が用意されていること

### リスク

- **Railwayのボリューム削除は不可逆**。一度削除すると、Volume内のデータ（`records.json`・`backups/`）は復元できない
- Volume削除後、**もし`STORAGE_BACKEND`が誤って`json`に戻された場合**（設定ミス・環境変数リセット等）、`logic.load_dates()`はファイルが存在しないため例外を出さず**空集合(`0件`)を返す**。これは「壊れている」とは検知されず、「まだ記録がない」ように見えてしまう——**静かな見た目上の障害**になり得る。この対策として、`storage.py`は将来、「一度でもpostgresへ切り替わった環境でjsonへ戻る場合は明示確認を要求する」といったガードを追加することも検討できる（本設計の範囲外、今後の課題として記録）
- Volume削除でproduction用Postgresの枠を作る場合でも、**stagingにPostgreSQL専用のVolume（`postgres-volume`）は引き続き必要**であり、削除できるのはJSON用の`web-volume-lbdR`のみである点に注意

### 結論

**今回は削除しない。** stagingでのPostgreSQL運用が実機で安定稼働することを確認し、上記条件をすべて満たしてから、改めて削除の可否をご判断いただく、という2段階の意思決定にする。
