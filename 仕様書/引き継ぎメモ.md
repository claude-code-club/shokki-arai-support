## ② ローカルで動かす

```bash
pip install -r requirements.txt
export DATABASE_URL="postgresql://..."   # postgresバックエンドを使う場合
export STORAGE_BACKEND=postgres          # 未設定時はjsonバックエンド(単一世帯)
streamlit run streamlit/app.py
```

マルチテナント・認証・課金以降の機能(第16回〜)はpostgresバックエンド専用。`AUTH0_*`/`STRIPE_*`関連の環境変数が未設定でも、`auth.is_auth_enabled()`/`billing.is_billing_enabled()`がFalseを返し、該当機能は自動的に非表示になる(落ちない設計)。

テストは`pytest tests/`。DB接続を要するテストは`DATABASE_URL`未設定時に自動スキップされる。`pg_dump`/`pg_restore`を要するテストは`PG_BIN_DIR`(ポータブルPostgreSQLのbinディレクトリ)未設定かつPATHに無い場合も自動スキップされる。

## ④ admin権限について(重要)

`tenant_memberships`テーブルのroleは**自動付与されない**設計(`仕様書/認証基盤設計.md`⑥)。`scripts/bootstrap_admin_membership.py`を、対象ユーザーの`auth_subject`と`tenant_id`を明示的に指定して実行した場合のみadminになる。

**auth_subject・メールアドレス等の個人情報は、方針としてチャット・ログ・ファイルのどこにも記録していない**(`仕様書/Stripe課金設計.md`に明記)。そのため「stagingの世帯で誰がadminか」を後から文書だけで追うことはできない。もし分からなくなった場合の再現手順:

1. 対象アカウントでstagingへログインし、メール確認まで完了させる(これで`users`テーブルに行ができる)
2. `bootstrap_admin_membership.py`を、そのアカウントの`auth_subject`(ログイン後の`st.user`から確認)と対象`tenant_id`を指定して実行する(**DBへの書き込みを伴うため、実行には都度、明示的な許可を得ること**)

## ⑤ 触ってはいけないもの・注意点

- `railway variable list`(デフォルトのテーブル表示)は環境変数の値をマスクせずそのまま表示する。**二度と使わない**(過去に実際の秘密情報が露出した事故がある)。値の確認が必要な場合は`railway run`で自動注入させ、値そのものを画面に出さない方法を使う
- `main`ブランチへの直接コミット・マージは、岩瀬様の明示的な承認を得てから行う(第16〜25回はすべてstaging止まりで意図的に保留されている)
- production・stagingのDBへ直接接続してのDDL・書き込みは、都度明示的な許可が必要(読み取り専用の確認であっても、最初は許可を取ってから行うのが安全)
- Windows環境でのテスト実行時、日本語の`[OK]`/`[NG]`出力を扱うsubprocessテストは`PYTHONIOENCODING=utf-8`が必要(無いと`UnicodeDecodeError`になることがある)
- ローカルの使い捨てPostgreSQL環境は`Claude Code`のセッションのscratchpad配下に作ることが多く、**セッションが終わると消える**。次回また必要になったら再構築が要る(本セッションでも前回セッション分の環境が消えていたため、ポータブルPostgreSQL 16を再ダウンロード・再構築した)
